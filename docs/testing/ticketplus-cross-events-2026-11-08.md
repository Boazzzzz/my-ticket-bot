## 已確認並修正的選票問題

Sweetnotes 是平面票種清單，指定 `1800` 後，原程式首次選票未成功取得指定列，
接著的全頁備援卻操作第一列 Earlybird NT$1,500，造成實際票種與指定 GA 不符。
嚴格張數驗收未將這次當成成功，也沒有按下一步或送出錯誤票種訂單。

後續將 Earlybird 歸零，再呼叫正式選票函式，診斷確認它能找到 GA 列並選到一張；
同頁其他票種張數均為零，才繼續到填寫資料頁。
目前證據不足以判斷首次指定列操作未成功的具體點擊原因；選取器能匹配 GA，
因此本輪沒有憑推測改選取器。

正式程式新增保護：有指定票區關鍵字時，指定列操作失敗會等待下次重試，
不再以全頁第一個加號取代指定票種。空關鍵字的既有備援保持原行為。
修正後尚未重新建立新訂單來驗證整段無人介入流程。

## GUI 無法自動走到最後一步的確認

使用者回報從 GUI 操作後沒有自動推進到最後一步。修正前查得：

- 當時保存的引擎為 Selenium，票數為 2；這是使用者自己的 GUI 設定，
  與前述每場一張的診斷測試不同，未更改該設定或拿它建立新的測試訂單。
- OCR 已啟用，但 `ocr_captcha.force_submit` 為 false，GUI 對應名稱為「掛機模式」。
  因此驗證碼辨識成功後也不會自動送出該步。
- `ticketplus_confirm()` 只呼叫 `ticketplus_ticket_agree()` 勾選 checkbox，
  沒有按「下一步」的程式。以本機離線 HTML 呼叫正式函式，實測結果為
  `terms_checked: true`、`next_button_click_count: 0`。
- `ticketplus_main()` 只有活動、選票與確認頁的對應處理，沒有 `/checkout/`
  的取票／付款方式與待付款訂單建立流程。
- 自動選票的前進動作綁在 OCR 分支；頁面沒有驗證碼時也缺少獨立的下一步處理。
  開啟「掛機模式」不能補上確認頁與付款方式頁尚未實作的步驟。

因此可以確認正式 GUI 的完整流程尚未串接，並非僅需開啟自動勾選。
尚未取得使用者這次卡住當下的畫面，不能斷言上述哪一個中斷點就是該次唯一原因。
本機重現只使用 data URL，未接受實站條款、未建立訂單或付款。

先前 VERA 的待付款訂單由診斷工具逐步操作完成，不能當作 GUI 無人介入購票的驗收。
當時先確認 GUI 中斷原因；後續選票頁修正如下。確認頁、ATM 待付款訂單建立
與實際付款仍是不同步驟，不能由選票頁前進成功推論完整流程已通過。


## 選完張數不按下一步：修正結果

使用者進一步確認卡在「選完張數後，沒有按下一步」。已針對 Selenium 正式程式修正：

- 將兩種遠大頁尾「下一步」選取器集中；按鈕已啟用時也會檢查前進條件，
  不再只在停用狀態處理選票及驗證碼。
- 掛機模式啟用且沒有可見驗證碼時，確認可見張數合計等於設定票數、
  所選票種符合指定關鍵字、下一步已啟用且沒有彈窗後，才按下一步。
- 有可見驗證碼時沿用 OCR／手動輸入分支，不能走無驗證碼的前進路徑。
- 活動專屬問答尚未完成、張數讀取失敗或數量／票種不符時不前進；
  同頁送出後十秒內不重複點擊，保留網站回應時間。
- 補上 `ticketplus_order_ocr()` 遺漏的提交結果回傳，讓呼叫端能辨識已送出狀態。

新增 15 項離線瀏覽器測試，完整回歸共 47 項通過，涵蓋兩種頁尾、
填張數後按鈕即時啟用、手動模式、已啟用按鈕、張數與票價、可見／隱藏驗證碼、
OCR 分支、未完成問答、彈窗及重複點擊防護。另通過 Python 編譯與 Git whitespace 檢查。
沒有用真實驗證碼做本輪驗收；OCR 測試只模擬回傳結果。

使用者本機目前「掛機模式」關閉，對應 `ocr_captcha.force_submit: false`；
這個模式仍保留手動按下一步。使用此自動前進修正時，需在 GUI 啟用「掛機模式」、
存檔後重新啟動機器人。此修改未變更使用者設定、帳密或其他售票平台。

驗收限制：修正僅以離線頁面驗證，尚未在實站重跑這段正式 GUI 流程；
