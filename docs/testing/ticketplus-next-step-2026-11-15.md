# 遠大選完張數不前進：2026-11-15 深入排查

## 設定與實站觀察

使用者本機設定為 Selenium、2 張、OCR 開啟、掛機模式開啟。
因此不能把本次問題直接歸因於未啟用掛機。最近啟動日誌兩次到達：

`/order/d269e0f5b10b35a2c56aaeb43f46d992/a2fb39de4266a939ae6cbaadcc07dec5`

活動為 [K-WONDER BAND STAGE IN TAIPEI](https://ticketplus.com.tw/activity/d269e0f5b10b35a2c56aaeb43f46d992)，
與前次高雄場不同。排查時原卡住的頁面已關閉，既有日誌沒有保存當時的實際張數
及提早返回原因，無法從舊日誌斷言使用者當時畫面已滿兩張。

沿用使用者授權的安全範圍，另存一張票、OCR 與掛機關閉的測試設定，透過
GUI 執行按鈕啟動正式程式及只讀診斷入口。活動頁一度顯示「暫無票券」，
之後開啟日誌記錄的原選票路由並填入一張，僅擷取控制項與截圖即退出。
未按下一步、接受條款、解驗證碼或建立訂單。

實際 DOM 的結果：

```json
{
  "visible_counts": [1],
  "configured_test_quantity": 1,
  "count_matches": true,
  "next_button": {"layout_style": 1, "visible": true, "enabled": true, "text": "下一步"},
  "has_captcha": false,
  "has_blocking_dialog": false,
  "plus_button_disabled": true
}
```

網站在一張時就啟用下一步，不能以按鈕可用推定已達到 GUI 設定的兩張。
本次實站加號有 `disabled`、`v-btn--disabled`，表示當下無法繼續增加；
不能只憑這個旗標區分庫存不足或會員限購。上述一張測試不能替代使用者先前
兩張設定的實際狀態，也不構成完整購票驗收。

## 已重現的程式缺陷

1. `ticketplus_order()` 只在下一步按鈕停用時補張數。一旦第一次只選到一張，
   網站先啟用下一步，後續迴圈就跳過補票，又因實際一張不符合設定兩張而返回。
   即使加號後來恢復可用，也會一直卡在這個狀態。
2. `ticketplus_assign_ticket_number()` 跨多次增加重用同一個計數器與加號元素。
   Vue 更新元素後，後續點擊或讀取可能遇到 stale element；例外被吞掉，
   而函式只要曾點一次就可能回傳成功，並未證明實際已填滿要求張數。
3. 多個阻擋條件直接回傳 false，日誌及 GUI 無法分辨張數、票區、彈窗、
   驗證碼、購票問題、手動模式、按鈕停用或點擊失敗。

這些缺陷可在本機穩定重現，但缺少原卡住頁的 DOM，仍不能宣稱它們涵蓋
使用者所有「畫面確實已有兩張仍不前進」的可能情況。

## 修正

- 依實際張數補票，不再用下一步是否可用決定是否補足。
  部分已選張數會補在原本符合票區設定的同一個票種，避免改加其他列。
- 每次增加前重新尋找計數器及加號按鈕，檢查按鈕是否可用，並等待實際數字
  增加；只有讀到等於要求張數才回報填寫成功。畫面替換可由下一迴圈重新取得。
- 張數過多、不明、票區不符、加號停用等情況保持送出保護；不把要求兩張
  擅自改成一張，不用 JavaScript 強制點擊停用加號或繞過彈窗。
- 所有主要停止原因寫入結構化日誌，狀態不變時最多每 30 秒輸出一次。
  GUI 顯示對應原因，例如目前一張／設定兩張、網站加號停用、等待驗證碼、
  等待活動問題、手動送出、彈窗阻擋、點擊失敗或等待導航。
- 保留函式回傳介面、設定格式、票區關鍵字、張數核對、驗證碼流程及
  10 秒重複送出防護。沒有修改其他平台的購票判斷。

## 驗證與限制

- 修正前新增的三個回歸案例均失敗：已啟用下一步但少一張、Vue 替換控制項、
  手動模式仍應補足張數。舊版均停留在一張。
- 修正版通過上述案例；掛機模式達到兩張後只點一次下一步，手動模式僅填票。
- 專項測試同時涵蓋已滿兩張且 OCR 開啟但無驗證碼、加號停用、錯誤票區、
  已選第二列、超額張數、真正／殘留彈窗、驗證碼、問題與重複送出。
- 整體 115 項回歸測試通過（51.402 秒），涵蓋既有遠大流程、GUI 啟動及新增
  原因提示；最後審查另加入排除票種的補票保護，31 項選票專項全部通過。
  購票點擊只在本機 HTML
  進行，沒有向實站送出下一步。真實 Tk GUI 配合隔離假機器人，也確認原因
  訊息能從子程序顯示到介面。通過 Python 編譯與 Git whitespace 檢查。

原始 DOM、截圖、診斷腳本與測試輸出只保留在忽略的
`.tools/next-step-diagnosis/`。測試暫存設定已刪除；使用者原有
`settings.json` 不提交。更新後必須重啟 GUI 與機器人，執行中的舊程序不會
自動載入新函式。

尚未驗證：在真實網站以兩張設定實際送出下一步，以及「實際已滿兩張仍卡住」
的現場 DOM。遇到後者時應保留頁面，使用新增的 GUI 原因與日誌繼續定位，
不要只憑另一場的一張票測試宣稱通過。
