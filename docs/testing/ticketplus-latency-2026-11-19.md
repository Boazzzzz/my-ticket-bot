# 遠大刷新與下一步延遲：2026-11-19

## 已確認的等待來源

使用者回報刷新及選完價位後按下一步緩慢。排查時使用者設定為 Selenium、
一張、掛機開啟、刷新間隔 0；沒有仍開啟的機器人驅動可量測實站耗時。
最近日誌有多次選中一張與按鈕替換重試，但沒有逐步計時，不能只憑日誌
將所有等待歸因於單一網站狀況。

以 `4352875` 的正式流程確認並在本機重現兩個額外等待：

1. 庫存查詢的結果檢查與刷新間隔共用節流。即使 JavaScript 已收到 ready，
   Python 仍回傳先前的 checking 狀態，直到一秒（或使用者更長間隔）後才繼續。
   已選張數也會先經過這道庫存檢查，pending 狀態還可能重整掉選擇。
2. 加號點擊後固定 `sleep(0.2)`，即使畫面已立即更新，也要等滿後才核對張數。

目前至少一秒的真正刷新間隔是前次穩定性修正的設計，確實與更早的密集刷新不同。
本次保留此間隔，改善的是結果已就緒及選票後仍被額外延遲的路徑。

## 修正

- 分開刷新節流與本機結果檢查；已發出庫存查詢後，每 50 毫秒最多讀取一次
  瀏覽器中快取的結果。JavaScript 仍每份文件最多執行一次 fetch，沒有提高
  網站查詢或整頁刷新頻率。
- 已有可見非零張數時，交給正常選票流程核對張數、票區、驗證碼與下一步，
  不再讓待開賣重查阻擋，也不從這條路徑刷新掉選擇。這不直接代表可送出。
- 尚未選票且庫存仍 pending 時維持等待，刷新未到時間不會因此放行。
- 加號改點實際可用的按鈕，將它捲至畫面中央，並等畫面數字實際增加後立即繼續。
  沒有固定 0.2 秒等待；每次增加重新取得計數器及加號，支援 Vue 替換控制項。
- 只有實際張數等於要求才回報成功；停用加號、未知／超額張數不會強制送出。
- 保留上一輪的 stale 按鈕保護、真正彈窗／驗證碼、十秒防重複提交、
  手動模式及付款結帳頁停止條件。

## 本機量測

相同 Windows、Chrome、正式 `ticketplus_main()`，使用本機 HTML，
模擬庫存 20 毫秒後回傳 ready。每種情境各量測三次，以下為中位數：

| 情境 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 張數已為 1，從進入處理到點下一步 | 1,254.53 ms | 223.23 ms |
| 張數由 0 開始，含庫存就緒、選一張及下一步 | 1,569.36 ms | 483.88 ms |
| 上一列中，畫面張數增加至下一步點擊 | 355.00 ms | 150.70 ms |

每輪只點一次本機下一步。從零選票的模擬 fetch 次數維持 1；
已選票情境由 1 次減為 0。沒有操作實站、送出新訂單或付款。
上述數字衡量客戶端等待，不代表實站網站回應、排隊、驗證碼或配票耗時。

量測腳本與原始數據留在本機忽略的 `.tools/benchmark_ticketplus_latency.py`、
`.tools/ticketplus-latency-before.json`、`.tools/ticketplus-latency-after.json`。
